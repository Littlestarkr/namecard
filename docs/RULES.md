# 명함 스캔 인식·보정 통일 규칙

> 대상: `index.html`의 명함 인식 파이프라인(Tesseract OCR + `parseCard` 후처리).
> 목적: 명함 한 장씩 땜질하던 방식을 멈추고, **같은 규칙으로 모든 명함을 다루기 위한 기준**을 한곳에 둔다.
> 표기: **[현재]** = 지금 코드가 이미 하는 일 / **[제안]** = 정했지만 아직 코드에 없음 / **[결정 필요]** = 작가님 판단이 필요한 것.

## 0. 기본 원칙

1. **엔진 한계를 인정한다.** Tesseract의 한글 인식은 약하다(2026-11-14 K Square 명함: 선명한 사진인데도 이름 `임계영`을 읽지 못함). 후처리는 *보정*까지만 하고, 정확도를 근본적으로 올리려면 엔진을 바꿔야 한다(§6).
2. **명함 한 장 때문에 규칙을 추가하지 않는다.** 틀린 명함이 나오면 ① `tests/cases.json`에 사례를 먼저 추가 → ② 그 사례를 포함해 **일반화된** 규칙으로 고침 → ③ `node tests/run.js` 전체 통과 확인. 특정 회사명·사람 이름을 코드에 넣는 것은 금지(기관 도메인 사전 `ORG_DOMAINS` 같은 공용 사전은 예외).
3. **확신이 없으면 틀린 값보다 빈 칸이나 후보를 낸다.** 자동 확정은 글자만으로 모호하지 않을 때만 한다. 모호하면 후보 칩(`alts`, `emalts`)으로 제시하고 사용자가 고르게 한다.
4. **한 칸에는 한 종류의 정보만 넣는다.** 이름 칸에 직책 글자, 회사 칸에 기호 찌꺼기가 들어가면 안 된다. 확신 없는 조각은 버린다.
5. **사진은 기본적으로 폰 밖으로 나가지 않는다.** 외부 서버(AI API 등)로 보내는 기능은 작가님의 명시적 승인과 안내 문구 변경 없이는 넣지 않는다.
6. **고친 뒤에는 `namecard-sw.js`의 `CACHE` 버전을 올린다.** 설치형 앱이 옛 코드를 계속 쓰는 것을 막기 위함이다.

## 1. 처리 순서 (파이프라인) [현재]

사진 선택 → 손질 화면(회전·모서리·기울기, `openEditor`) → `handle()`
→ 방향 판별(`pickRotation`) → 명함 위치 찾아 자르기(`textExtent`) → 기울기 보정(`estimateSkew`)
→ 4회 읽기(블록 모드 color → adaptive → color(11) → invert, `modes`) → `mergeLines`로 줄 합치기
→ `parseCard`(필드 분리) → 재읽기(`refineName`·`recoverNameNearTitle`·`findDept`·`refineEmail`)
→ 보정(`reconcileOrg`·`fixEmail`·`fixWeb`·`fixOrg`·`cleanAddr`) → 칸 채우기 + 후보 칩.

`parseCard`는 **먼저 확정한 줄을 `used`로 잠그고 다음 단계에서 제외**한다. 순서가 곧 우선순위다:
이메일 → 웹 → 전화(T/F/M·내선) → `부서|직책` 구분자 줄 → 주소 → 구분자(`| / ·`) 줄 → 직책·회사·부서 키워드 줄 → 로고형 회사명 → 이름 → 영문 이름 → 보정.
**순서를 바꾸면 모든 명함에 영향이 가므로, 바꿀 때는 반드시 전체 시험을 돌린다.**

## 2. 필드별 규칙

### 이메일
- 추출 **[현재]**: `x@y.tld` 패턴. `e-mail:` 접두어 제거, 도메인 안의 공백 제거, `-com` → `.com`.
- 보정 **[현재]**: `orkr`→`or.kr`처럼 빠진 점 복구, 알려진 기관 도메인(`ORG_DOMAINS`)과 1글자 차이면 맞춤(`fixEmail`).
- 모호 글자 **[현재]**: `0/o`, `1/l/I`는 **자동 확정하지 않고** `emailAlts`로 후보 칩을 낸다. 끝자리 `l`·`I`는 `1`일 가능성이 높아 후보 맨 앞(2026-11-14 추가).
- 금지: 아이디 부분(`@` 앞)을 사전·추측으로 바꾸지 않는다.

### 웹사이트
- 추출 **[현재]**: `www.`/`http(s)://`/`도메인.(com|co.kr|net|org|io|kr)`.
- 보정 **[현재]**: 끝이 잘린 `.or`/`.co` → `.kr` 추가. 웹이 비면 이메일 도메인으로 `www.도메인` 채움(gmail·naver 등 공용 메일은 제외).

### 전화번호
- 추출 **[현재]**: 줄 전체에서 `O/o→0`, `l/I/|→1`로 바꾼 뒤 번호 패턴 추출 (**숫자 자리에서는 강제 치환이 안전**).
- 분류 **[현재]**: 라벨(Tel/Fax/Mobile·전화/팩스/휴대폰) 우선, 라벨이 없으면 `01x`로 시작하면 휴대폰, 아니면 회사 전화. 내선은 `[123]`·`내선 123`·`ext`.
- 같은 번호는 중복 저장하지 않는다.

### 주소
- 추출 **[현재]**: 시·도명 / `○○시·군·구` / `○○로·길 + 숫자`가 있고 숫자가 있는 줄. 이어지는 줄(읍·면·동·로·길·층·호·빌딩·`N층`)은 최대 2줄 붙임.
- 정리 **[현재]** `cleanAddr`: 맨 앞 1~2자 영숫자 아이콘 찌꺼기(`O `) 제거, 줄 끝·중간의 `^ ~ | _ \`` 제거, `로/길` 뒤 번지 앞 공백 삽입.

### 직책
- 추출 **[현재]**: `titleRe`/`TITLE_WORDS`의 직책 단어(대표·이사·부장·컨설턴트·변호사·경영지도사 등). 영문 직책도 인식.
- **직책 단어뿐인 줄은 이름 후보에서 제외한다 [현재]** (이름 줄 판별 두 곳 모두).
- `파트너`는 `파트너스/파트너즈`(회사명)와 구별한다 [현재].
- **복합 직책은 보존한다 [현재, 2026-11-14 결정]**: 직책 단어를 모두 살려 공백으로 잇는다(`대표 컨설턴트`). 구분자(`/ | · ,`)·공백으로 나눈 조각마다 직책 단어로 확인하고(`keepTitles`), 영문 꼬리는 제거한다. 직책 단어가 하나도 없으면 첫 일치 단어(없으면 원문).
- 오인식된 직책 글자는 자모 거리로 가까운 직책 단어에 맞춘다 [현재 `fuzzyTitle`, 거리 ≤1(5자 이상은 ≤2)]. `커설턴트`→`컨설턴트`.
- 직책 아래 **별도 줄의 자격명**(`경영지도사` 등 직책 단어뿐인 줄)은 직책 뒤에 ` / `로 덧붙인다 [현재, 2026-11-14 결정]: `대표 컨설턴트 / 경영지도사`. 직책이 없으면 덧붙이지 않는다. `/ | · ,`로 나뉜 직책 묶음은 그대로 유지한다.

### 회사
- 추출 **[현재]**: `orgRe`(주식회사·㈜·은행·공사·공단·협회·재단·센터·그룹·파트너스·컨설팅·컴퍼니·법인·사무소 …) 줄 → 한글&한글 로고 줄 → 한글 로고 앞부분 → 영문 `… Investment/Partners/…` 줄.
- 보정 **[현재]**: 이메일·웹 도메인·로고 글자(KIBO 등)로 알아낸 기관명과 거의 같으면 그 이름으로 교체(`reconcileOrg`).
- 회사 칸 값은 **앞뒤 기호·점·밑줄·낱글자 찌꺼기를 제거**한다 [현재 `cleanOrg`, 2026-11-14]: `` ` … 케이스퀘어 파트너스 _럴`` → `케이스퀘어 파트너스`. 시작은 한글·영문·숫자·`(`·`㈜`만 허용, `_ | ~ ^ \`` 뒤의 2글자 이하 꼬리는 잘라냄. 기관명 끝 단어(파트너스·컨설팅·은행·공사·센터·그룹 등) 뒤에 공백으로 떨어진 **한글 1글자**(`파트너스 뿔`)도 잘라냄. `법무법인 세종`처럼 앞에 붙는 단어(법인·주식회사)는 대상이 아님.

### 부서
- 추출 **[현재]**: `deptRe`(본부·팀·실·지점·사업부·영업·연구소 …). 못 찾으면 이름·직책 줄 바로 아래 작은 글씨를 다시 읽는다(`findDept`).
- 부서로 확정되지 않은 글자는 비운다(`deptRe` 불일치 시 `''`).

### 이름
- 추출 **[현재]**: 한글 2~4자 단독 줄, `이름 직책` 한 줄, `이름 / 직책`처럼 구분자로 이어진 줄의 이름 조각(2026-11-14 추가), `한글이름 영문이름` 줄, 영문 2~3단어 줄.
- 제외 **[현재]**: 회사·부서·직책 키워드 줄, 숫자 덩어리가 있는 줄, 로고형 줄(`&`, `수·오·재`).
- 재확인 **[현재]**: 인식된 한글 이름이 없거나 **2글자뿐이면** 직책 주변을 다시 읽는다(`recoverNameNearTitle`, 2026-11-14 추가). 헷갈리는 모양은 `altNames`로 후보 칩 제시(받침 빠짐·ㅗ/ㅜ·ㅁ/ㅂ/ㅇ).
- 직책 단어(오인식 포함)로만 이뤄진 줄은 **이름으로 쓰지 않는다** [현재 `isTitleLike`, 2026-11-14]: 3글자 이상 조각이 `fuzzyTitle`로 직책에 맞춰지면 직책형. `대표커설턴트`처럼 `대표`+직책형 조합도 이름으로 보지 않는다(`splitNameTitle`). 2글자 조각은 실제 이름과 겹칠 수 있어 직책형 판정에서 뺀다.
- `이름 + 직책 여러 단어`(`홍길동 파트너 변호사`)는 이름과 직책으로 나눈다 [현재, 한글 12자까지].
- 금지: 이름 글자를 사전으로 자동 교체하지 않는다. 후보는 칩으로만 낸다.

## 3. 숫자·문자 혼동 처리 기준

| 위치 | 규칙 |
|---|---|
| 전화번호 안 | `O/o→0`, `l/I/\|→1` **자동 치환** (숫자만 올 자리) |
| 이메일 아이디 | 자동 치환 **금지**, 후보 칩만 제시 (끝자리 `l/I→1`, `o/O→0` 우선) |
| 이메일 도메인 | 알려진 도메인과 1글자 차이면 자동 교정 |
| 한글 이름 | 자동 교체 금지, 후보 칩 |
| 회사명 | 로고 글자·도메인과 일치할 때만 교정 |

## 4. 시험과 변경 절차

- 시험: `node tests/run.js` — 텍스트 수준 회귀 시험(실제 OCR은 브라우저에서만 돈다).
  `tests/cases.json`의 `todo: true`는 "알려진 미해결". 고치면 스크립트가 `★ 이제 통과`를 알려 주니 `todo`를 지운다.
- 변경 순서: 사례 추가 → 일반 규칙 수정 → 전체 시험 통과 → `CACHE` 버전 올림 → 커밋.
- 한계: 같은 명함도 **자르는 범위가 달라지면 OCR 결과가 달라진다**. 그래서 실제 사진 검증은 폰에서 직접 해야 하고, 위 시험이 통과해도 인식률이 보장되지는 않는다. 새 오인식이 나오면 `인식된 원문 보기`의 텍스트를 사례로 추가하는 것이 가장 좋다.

1. 선명한 명함에서도 한글 이름을 못 읽는 경우가 있다 — 엔진 한계(§6).

## 엔진 결정 갱신 (2026-11-14)
- 작가님 폰 시험(paddle-test.html, 여러 장)에서 PaddleOCR 한국어(PP-OCRv5 mobile)가 Tesseract보다 이름·회사·직책이 정확하고 빨랐다(예: 3.0초 vs 8.4초).
- 본 앱 기본 엔진을 PaddleOCR로 바꾸고, 로딩·인식 실패 시 기존 Tesseract 경로로 자동 전환한다. 사진은 계속 폰 안에서만 처리(모델·엔진 파일만 내려받음, 최초 약 20MB, 서비스워커 `ocrmodels-v1` 캐시에 보관).
- Paddle 경로는 Tesseract 전용 보정(refineName·refineEmail·findDept·회전/자르기)을 쓰지 않는다. 사진 손질 화면의 결과를 그대로 읽고 parseCard → reconcileOrg → 이메일 후보 칩만 적용.
- 할 일: Paddle 원문(화면의 '원문' 칸)을 tests/cases.json 사례로 쌓고, 필요하면 일반 규칙을 보강한다.
- 자격(박사·지도사·세무사 등)은 항상 직책 뒤에 ' / '로 둔다. 명함에 자격이 먼저 적혀도 '대표이사 / 경영학박사' 순서(2026-11-14, 학위: 경영학·공학·법학 등 'X학박사').
- 같은 사진을 두 번 읽은 이메일(원본 읽기·확대 읽기)이 0/o·1/l 에서만 다르면 숫자 옆 글자는 숫자 쪽을 따른다(mergeEmailVotes, 두 읽기가 근거라 자동 교체 금지 원칙 위반 아님).
- 전화번호는 숫자만 뽑아 국내 자릿수 규칙(02·050x·0xx)으로 하이픈을 다시 넣는다(fmtKrPhone). 주소의 쉼표 뒤에는 공백을 둔다.
- 이름 줄에 학위가 붙은 경우('마선옥 컨설팅학 박사')는 이름+자격으로 나누고 '학 박사' 띄어쓰기는 붙인다. 회사명 뒤에 직책이 붙은 줄('(주)꿈제작소 대표이사')은 회사/직책으로 나눈다. 주소 둘째 줄(타워·빌딩·호)은 이어 붙인다.

## 방향·속도·이름 규칙 (2026-11-14, v48)
- 세로(옆으로 누운) 명함: 첫 읽기에서 글자 상자의 절반 이상이 세로로 길면 90°→(필요 시)270°로 돌려 읽고 점수(신뢰도×글자수)가 더 높은 쪽을 쓴다. 평균 신뢰도가 낮으면 180°를 한 번 시도. 확신이 없으면 원래 방향 유지.
- 속도: 첫 읽기 최대 1280px, 크게 다시 읽기 최대 1500px(이전 1600/1800). 정확도가 떨어지면 되돌릴 것(폰 실측 필요).
- 이름 줄 끝의 영문 병기 괄호 `(LEO KO)`는 떼고 이름·직책을 판단한다. 한글 괄호 `(주)`는 건드리지 않는다.
- `+82-(0)10-…` 형식은 `010-…`으로 읽는다.
- 주소 이어붙이기는 한글이 있는 줄만(영문 주소 줄은 붙이지 않는다).
- 이름 후보: 직책 줄('대표') 바로 아래(없으면 위) 한글 줄 우선. 같은 한글이 다른 줄에도 있는 줄(로고·회사명 반복)은 다른 후보가 있을 때 이름에서 제외 (v49)
- 이메일 0/o·1/l 후보는 모든 조합을 만들어 글자↔숫자 전환 적고 숫자로 끝나는 순으로 앞 6개(kokumalo→kokuma10 포함). 주소의 번지·호수는 영문 줄(11-41, #904)과 교차 확인해 빠진 자리·깨진 글자를 맞춘다 (v50)
